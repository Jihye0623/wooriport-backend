# Phase 4 — 현실 카디널리티 부하 (소비 피크 시뮬레이션)

- 코드: `exp/kafka-3-tuning` 재사용 (운영 로직 변경 없음 — 실험 조건만 변경)
- 기준선: Phase 3 (18카드, 포화 드레인) 결과
- 측정: 2026-06-09, AMD Ryzen 5 5600X (6C/12T), RAM 16GB, Windows 11

> **왜 Phase 4 인가 — Phase 3 의 논리적 한계**
> Phase 0~3 은 "코드/설정 한 변수만 바꾸고 나머지 고정"으로 묶인 **컨슈머 용량(포화 백로그 드레인) 비교** 실험이다.
> 거기서 데이터셋은 **카드 18장(고유 키 18)** 으로 고정했는데, 이는 파티션당 키 ≥ 3 을 p6 까지만 보장한다.
> 그래서 Phase 3 의 "p12 최적" 결론에는 **키 스큐**(일부 파티션 과부하·일부 idle) 가 섞여 있다.
>
> "현실 소비 피크"의 본질은 **많은 카드가 동시에 거래**(고 카디널리티) 인데, 18장으론 이를 대표할 수 없다.
> Phase 4 는 **카디널리티 하나만** 18 → 수천으로 올려, Phase 3 의 파티션 결론이 키 스큐 없이도 유지되는지 검증하고,
> 나아가 **지속 도착률에서 시스템이 따라잡는 최대 TPS** 를 측정한다.

## 3. 트랙 A — 카디널리티 영향 (파티션 스윕 재현)

**목적**: 키가 균등분산되면 Phase 3 의 파티션×concurrency 곡선/최적이 유지되는가?

**부하**: rate=0 버스트, N=100k (Phase 3 와 동일 조건 → 직접 비교).
**스윕**: partitions = concurrency ∈ {3, 6, 12, 24}, mpr=2000 고정.

| Run | partitions | concurrency | persist wall-clock | persist p50/p95 | E2E max | 처리량 (msg/s) | Phase3 동일설정(18키) 대비 |
|-----|-----------|-------------|------------------|-----------------|--------|--------------|--------------------|
| P4A-3  | 3  | 3  | 15.31 s | 801 / 1137 ms | 30.88 s | **3,238** | 2,307 → **+40%** |
| **P4A-6**  | **6**  | **6**  | 10.99 s | 1005 / 1676 ms | 30.55 s | **3,273 ← 피크** | 2,591 → **+26%** |
| P4A-12 | 12 | 12 | 7.13 s | 904 / 2816 ms | 31.11 s | 3,214 | 3,137 → +2% |
| P4A-24 | 24 | 24 | 4.85 s | 602 / 3488 ms | 31.03 s | 3,222 | (Phase3 없음) |

> **결과**: 고카디널리티에서 **처리량이 ~3,250 msg/s 에서 즉시 평탄화**(p3 부터). 파티션을 6→12→24 늘려도
> throughput 은 불변, **p95(꼬리 지연)만 1137→3488 ms 로 악화** → 더 쪼개도 이득 없이 경합만 증가.
>
> **Phase 3(18키) 대비 동일설정에서 +26~40% 빠름** — 18키일 땐 키가 소수 파티션에 몰려 **스트래글러**(가장 무거운
> 파티션의 마지막 메시지가 E2E_max 지배)가 처리량을 저평가시켰다. 5,000키면 완전 균등 → 스트래글러 제거.
> → **Phase 3 의 "p12 최적"은 저카디널리티 아티팩트**였고, 현실 분포의 진짜 최적은 **p6**.
> 진짜 병목은 파티션이 아니라 **DB persist**(~3,250 천장)임이 확정됐다. (persist p50 가 카디널리티로 801ms↑ —
> `findByAssetNumberIn` 의 distinct asset 이 배치당 최대 2000개로 커진 탓, 그래도 균등분산 이득이 우위.)

## 4. 트랙 B — 지속 도착률 (피크 감당 TPS)

**목적**: 고정 TPS 를 지속 주입할 때 **컨슈머 lag 이 평형인 최대 도착률** = 시스템이 밀리지 않고 감당하는 피크.

**설정**: 트랙 A 최적 파티션/concurrency 고정 · mpr=2000 · 카드 5,000.
**부하 모델**: rate=R msg/s 로 **지속 시간 T=180s** 주입 (총건수 = R×T, N 고정 아님).
**관측**: 컨슈머 그룹 lag 시계열 (kafka-consumer-groups LAG 합, 2~3s 폴링).

> **N 을 고정하지 않는 이유**: 트랙 B 가 보는 건 "총 드레인"이 아니라 "시간에 따른 lag 추세"다.
> 추세 판정에는 **지속 시간**이 필요(짧으면 평형/증가 구분 불가). 총건수는 R×T 로 파생된다.

**도구(신규)**: `phase4_rate_producer.py` (rate 정밀 페이싱, flush/print 병목 제거) + `track-b-lag.ps1` (lag 폴링 → CSV).

**스윕**: R ∈ {2500, 2800, 3000, 4000} (천장 부근 무릎 탐색). 발행 = `phase4_rate_producer.py`(20ms 틱 페이싱).
lag(t) = `목표 R × 경과 − transactions COUNT(t)` (COUNT 폴링이 kafka-consumer-groups 보다 부하 중 견고).

| Run | 목표 TPS | 실제 발행 | 지속 컨슈머율 | lag 기울기 | 주입 후 lag | 판정 |
|-----|---------|---------|------------|-----------|-----------|------|
| P4B-2500 | 2500 | 2,500/s | 2,517 | **−6.6 /s** | ~150 (평형) | **감당** |
| **P4B-2800** | 2800 | 2,800/s | 2,771 | **+22.6 /s** | ~7,800 | **무릎(지속한계)** |
| P4B-3000 | 3000 | 2,999/s | 2,822 | +169 /s | ~26,000 ↑ | 밀림(경계) |
| P4B-4000 | 4000 | 3,999/s | 2,855 | +1,177 /s | ~142,000 ↑ | 밀림(과부하) |

> 판정은 **lag 기울기**로: ≈0 이면 감당, 양수 지속이면 밀림. 기울기 = (목표 − 지속 컨슈머율).
> 2500 음수(평형) · 2800 거의 0(무릎) · 3000+ 양수(누적). → **최대 지속가능 ≈ 2,800 msg/s.**
> 지속 컨슈머율 천장(~2,800~2,855) < 트랙 A 버스트 천장(3,273) ≈ **85%**: 지속 주입 시 producer 와 consumer 가
> **같은 박스 CPU 를 경합**하기 때문(버스트는 producer 가 먼저 끝나 consumer 가 박스를 독점). 현실 동시부하에 더 가까운 수치.

## 5. 결론 (측정 완료, 2026-06-09)

1. **병목 = DB persist (확정)**: 카디널리티를 18→5,000 으로 올려도 처리량 천장은 **~3,250 msg/s 로 불변**,
   파티션을 p3→p24 늘려도 throughput 불변(p95 만 1137→3488 ms 악화). 카프카·파티션·스레드가 아니라 **DB 적재가 천장**.
2. **파티션 사이징 — Phase 3 결론 수정**: Phase 3 의 "p12 최적"은 18키 스큐가 만든 **스트래글러 아티팩트**였다.
   현실 카디널리티의 진짜 최적은 **p6×c6 (3,273 msg/s)**. 그 이상은 꼬리 지연만 늘린다.
3. **피크 감당 TPS = ~2,800 msg/s**: 지속 주입에서 lag 평형을 유지하는 최대 도착률 ≈ **2,800/s**.
   초과 시(3,000+) lag 단조 증가(밀림). 운영 용량 헤드룸 ≈ **2,800 TPS (≈ 1,000만 건/시간)**.
4. **교차검증 성립**: 버스트 천장 3,273(트랙 A) vs 지속 천장 ~2,855(트랙 B) — 같은 DB 한계를 다른 방법으로 확인.
   지속이 버스트의 ~85% 인 차이는 producer/consumer 의 **동일-박스 CPU 경합**(현실 동시부하에 가까운 보수적 수치).
5. **forward (Phase 5 후보)**: 카프카측(파티션·배치·concurrency) 튜닝은 한계 도달. 추가 용량은 **DB 레버**에서 —
   HikariCP 풀 확대, `jdbc.batch_size` 조정, 디스크 IOPS, transactions 테이블 파티셔닝/인덱스 최소화.

> **전체 서사 종합**: Phase 0~3 은 컨슈머 **처리량 천장을 305 → 3,137 msg/s** 로 올렸고(상대 개선),
> Phase 4 는 그것을 현실 분포에서 **운영 용량 = 지속 ~2,800 TPS(≈1,000만 건/시간)** 라는 실물 숫자로 번역했다.
> 그리고 다음 병목이 카프카가 아니라 **DB** 임을 두 방법(카디널리티 불변성 + 버스트/지속 교차검증)으로 확정했다.
